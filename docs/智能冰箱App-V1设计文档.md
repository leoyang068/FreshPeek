# 智能冰箱 App V1 完整设计文档

> 版本：V1.0 设计稿
> 日期：2026-08-21
> 适用范围：树莓派识别端、Supabase 数据层、iOS SwiftUI App 及菜谱生成服务

---

## 1. 产品定位

智能冰箱 App 是智能冰箱食材识别系统的手机端。它不要求用户持续手工记账，而是接收树莓派摄像头和多模态模型产生的入库、出库事件，自动维护食材库存。

V1 的核心目标是：

1. 打开 App 后，立即看见最需要优先处理的食材。
2. 自动完成大部分入库和出库操作。
3. 模型无法可靠匹配时宁可不删除库存，避免静默删错。
4. 用户可以快速纠正名称、保质期和错误库存。
5. 用户可以选择临期食材，按需生成菜谱。

V1 不记录库存数量，只记录某种食材或某个包装是否仍在冰箱中。对于一盒鸡蛋，放入时只记录“鸡蛋存在”；从盒中取出一个或多个鸡蛋不减少库存，直到整盒鸡蛋被取出。此类“容器与内部数量”识别暂不在 V1 实现，但作为后续版本需求保留。

V1 只服务一台冰箱和一部手机，使用一个手动创建的 Supabase 邮箱账号。App 不提供注册、家庭成员邀请、多冰箱切换或角色管理界面。数据库继续保留 `owner_id` 并通过 RLS 限制数据归属，为后续多人共享预留接口，但 V1 不实现多人业务逻辑。

## 2. V1 功能范围

### 2.1 包含

- 卡通打开冰箱造型的库存首页。
- 按到期时间从近到远排列的食材瀑布流。
- 柔和的红、橙、绿三种保质期状态。
- 食材名称和保质期编辑。
- 手动添加食材。
- 左滑删除与短时间撤销。
- 自动入库、同名绿色食材合并。
- 自动出库、名称优先匹配和全库存图片兜底匹配。
- 入库最佳帧保存到云端，但不在普通界面显示。
- 菜谱食材选择模式和按需生成菜谱。
- 菜系偏好设置。
- 厨师思考加载动画。
- 树莓派同步状态和基础错误提示。
- 后台识别事件日志，供调试和后续模型优化。

### 2.2 暂不包含

- 对每个散装食材进行可靠的个体追踪。
- 基于本地视觉向量的相似度检索。
- 自动读取包装上的生产日期和保质期。
- 用户社交、菜谱社区和购物清单。
- 在库存列表中展示食材参考照片。

## 3. 视觉与布局设计

## 3.1 整体造型

主界面是一台打开的卡通冰箱：

- 页面外框形成圆角冰箱柜体。
- 顶部保留冰箱内灯、冷气或轻微高光等装饰。
- 内容区像冷藏室内部，从上到下连续滚动。
- 食材条目之间可以用浅色层板分隔，形成冰箱货架感。
- 冰箱门、门框和把手只作为视觉装饰，不侵占主要内容。
- 页面整体使用奶白、浅蓝灰和低饱和状态色，避免刺眼。
- 视觉语言为卡通、生活化、手帐风格：轻微纸张纹理、手绘边线、胶带贴纸、圆润图标和少量食物涂鸦。
- 手帐装饰只用于营造亲切感，不能遮挡食材名称、保质期或滑动操作。

库存不是多列 Pinterest 式布局，而是单列、连续、容易阅读的纵向瀑布流。

## 3.2 顶部区域

顶部包含：

- 标题：`我的冰箱`。
- 一行低调小字显示最后同步时间，例如 `最后同步：2 分钟前`。
- 右上角设置按钮。

不显示库存总数。同步状态应低调显示；只有设备长时间离线或同步失败时，才将最后同步时间改为提醒状态。

## 3.3 食材排序

食材始终按以下规则排序：

1. 已过期食材排最上方。
2. 到期时间越近越靠上。
3. 到期时间相同时，最近更新的条目靠前。

用户修改保质期后，列表自动重新排序，并使用柔和动画移动到正确位置。

## 3.4 状态颜色

默认状态规则：

| 状态 | 条件 | 颜色方向 | 行为 |
|---|---|---|---|
| 红色 | 已超过到期日 | 低饱和粉红/砖红 | 不自动加入菜谱 |
| 橙色 | 今天到期或剩余 1–3 天 | 低饱和杏橙 | 菜谱模式自动勾选 |
| 绿色 | 剩余 4 天及以上 | 低饱和鼠尾草绿 | 可手动加入菜谱 |

颜色不能是唯一的信息表达方式。每个条目必须同时显示文字，例如：

- `已过期 1 天`
- `今天到期`
- `还剩 2 天`
- `还剩 12 天`

临期天数应允许在设置中修改，默认值为 3 天。

## 3.5 食材条目

普通状态下，每个条目显示：

- 食材名称。
- 保质期状态，例如 `还剩 2 天`。
- 可选的入库日期小字。
- 低调的编辑图标或点击编辑能力。

入库保存的最佳帧不在库存页面、详情页或菜谱页显示，只供后台出库匹配使用。

## 3.6 编辑交互

点击食材名称或保质期区域，弹出轻量编辑面板。可修改：

- 食材名称。
- 入库日期。
- 保质期天数或到期日期。

界面只显示一个食材名称。`canonical_name` 属于后台匹配字段，不在 App 中展示或单独编辑；用户修改食材名称后，后台根据修改后的名称重新生成标准名称。保存后立即重新计算状态和排序。所有手动修改写入审计字段，防止后续自动识别覆盖用户修正。

## 3.7 手动添加

首页标题右侧提供圆形 `＋` 按钮。点击后可以填写：

- 食材名称。
- 入库日期。
- 保质期天数。

输入名称时优先查询保质期参考表并自动填写已有天数，用户仍可修改。手动添加使用修改后的名称作为后台标准化输入，并遵守普通入库规则：已有同名绿色条目时合并且采用更早到期日；同名橙色或红色条目不与新鲜批次合并。

## 3.8 左滑删除

条目左滑后露出红色删除按钮，交互类似微信聊天删除：

1. 第一次左滑只显示删除按钮。
2. 点击删除后从列表移除。
3. 页面底部短暂显示 `已删除“牛奶” · 撤销`。
4. 撤销时间建议为 5 秒。
5. 超过撤销时间后执行软删除，后台仍保留审计记录。

## 4. 数据模型

## 4.1 inventory_items：库存条目

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 条目唯一标识 |
| food_name | Text | 用户看到的名称 |
| canonical_name | Text | 标准化后的匹配名称 |
| added_at | Timestamp | 首次入库时间 |
| last_added_at | Timestamp | 最近一次合并入库时间 |
| shelf_life_days | Integer | 当前采用的保质期天数 |
| expiry_date | Date | 当前最早到期日 |
| status | Text | red/orange/green，可实时计算 |
| user_corrected | Boolean | 是否经过用户手动修正 |
| appearance_profile | JSONB | 预留的外观结构化特征，V1 可为空 |
| created_at | Timestamp | 创建时间 |
| updated_at | Timestamp | 更新时间 |
| deleted_at | Timestamp? | 软删除时间 |

`status` 可以不持久化，由 `expiry_date` 和设置中的临期天数动态计算。若持久化，应每天重新计算。

## 4.2 inventory_reference_images：后台参考图片

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 图片记录 ID |
| inventory_item_id | UUID | 对应库存条目 |
| storage_path | Text | Supabase Storage 私有路径 |
| source_event_id | UUID | 来源识别事件 |
| frame_index | Integer | 在本次连拍中的序号 |
| target_clarity | Text | 目标清晰度：good/usable/poor |
| hand_occlusion | Text | 手部遮挡程度：low/medium/high |
| is_primary | Boolean | 是否为当前主要参考图 |
| created_at | Timestamp | 创建时间 |

合并入库后，可以给一个库存条目保留多张参考图片，但 V1 默认最多保留 3 张：

- 优先保留清晰度高的图片。
- 优先保留外观差异明显的图片。
- 超出上限时删除最差或最旧的非主要图片。

图片存储在私有 bucket 中，不提供公开 URL。App 普通界面不请求这些图片。

## 4.3 recognition_events：识别事件日志

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 事件 ID |
| direction | Text | in/out |
| raw_result | JSONB | 模型原始返回内容 |
| normalized_result | JSONB | 清理和标准化后的结果 |
| action | Text | created/merged/deleted/restored/no_action |
| matched_inventory_id | UUID? | 匹配到的库存条目 |
| decision_reason | Text | 系统决策原因 |
| created_at | Timestamp | 事件时间 |

未匹配的出库事件不在普通库存 UI 中展示，但必须记录为 `no_action`，便于后续核查和优化。

## 4.4 user_settings：用户设置

只包含：

- 临期阈值天数，默认 3。
- 默认菜系。
- 是否接收临期提醒。

## 4.5 shelf_life_rules：食材保质期参考表

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 规则 ID |
| canonical_name | Text | 标准食材名称，唯一索引 |
| shelf_life_days | Integer | 冷藏条件下的默认保质期 |
| assumption | Text | 估算前提，例如未开封、普通超市包装 |
| source | Text | llm/user/system |
| created_at | Timestamp | 首次记录时间 |
| updated_at | Timestamp | 更新时间 |

第一次出现某种食材时，系统让 LLM 根据“普通超市购买、放入家用冰箱冷藏”的默认场景给出一个保守的常见保质期，并写入此表。以后同名食材入库时优先查询此表，不再重复询问 LLM。

如果具体包装上存在明确日期，V1 仍以参考表为默认值，由用户手动修正。用户修改某一库存条目的保质期不会自动覆盖全局参考表，避免一次特殊情况影响以后所有同名食材。

## 5. 入库识别接口

Qwen-VL 每次开门事件应为每个识别到的食材返回：

```json
{
  "foods": [
    {
      "name": "纯牛奶",
      "canonical_name": "牛奶",
      "direction": "in",
      "best_frame_index": 17,
      "target_clarity": "good",
      "hand_occlusion": "low",
      "recognition_confidence": "high",
      "appearance_summary": "白色长方体纸盒，蓝色文字，顶部白色旋盖"
    }
  ],
  "gesture": false,
  "reason": "牛奶从门外移动到冰箱内部",
  "confidence": "high"
}
```

### 5.1 最佳帧要求

`best_frame_index` 应选择：

- 食材主体最大且最清楚。
- 遮挡最少。
- 运动模糊最轻。
- 包装、颜色、形状或纹理最容易辨认。
- 如果多件食材同时出现，每个食材可以返回不同的最佳帧。

如果没有可用画面，仍可创建库存，但 `target_clarity = poor`，且不保存参考图片。

### 5.2 由 LLM 判断清晰度、遮挡和最终置信度

后端不再计算加权分数，也不增加额外的一致性字段。Qwen-VL 在完成食材名称、方向和最佳帧判断后，继续依次判断：

1. 最佳帧中的目标是否清楚。
2. 目标被手或其他物体遮挡了多少。
3. 综合画面证据以及它对名称和方向判断的把握，直接返回最终 `recognition_confidence`。

识别 prompt 中加入以下要求：

```text
在确定每个食材的名称、进出方向和最佳帧后，请继续完成以下判断：

1. 判断最佳帧中目标食材的清晰度 target_clarity：
   - good：主体清楚，关键外观或包装特征容易辨认；
   - usable：存在轻微模糊，但仍能辨认主要特征；
   - poor：严重模糊、主体过小或关键特征无法辨认。

2. 判断目标被手或其他物体遮挡的程度 hand_occlusion：
   - low：几乎无遮挡；
   - medium：部分遮挡，但主要特征仍可见；
   - high：大面积遮挡，关键特征不可见。

3. 最后请综合考虑：
   - 你对食材名称判断的把握；
   - 你对 in/out 方向判断的把握；
   - target_clarity；
   - hand_occlusion；
   直接给出最终 recognition_confidence：high、medium 或 low。

不要返回数值分数或额外的一致性字段，也不要让后端再次加权计算。
每个食材必须返回 target_clarity、hand_occlusion 和 recognition_confidence。
```

后端原样保存这三个字段，并直接使用 `recognition_confidence` 做业务判断。

### 5.3 图片处理

V1 建议：

1. 从连拍中取出最佳帧。
2. 若模型能够返回主体框，则裁剪主体；不能返回时先保存整帧。
3. 将长边压缩到约 768–1024 像素。
4. 移除不必要的元数据。
5. 上传私有云存储。
6. 原始连拍短期保留后清理。

### 5.4 Pi 到云端事件接口

树莓派只把每个食材的最佳帧上传到 `ingest-event` Edge Function，不上传全部连拍。请求使用 `x-fridge-device-token` 独立设备凭证；Pi 不保存 Supabase Secret key。

```json
{
  "event_id": "一次开门事件的 UUID",
  "captured_at": "2026-08-22T12:00:00Z",
  "gesture": false,
  "foods": [
    {
      "name": "纯牛奶",
      "canonical_name": "牛奶",
      "direction": "in",
      "best_frame_index": 17,
      "best_frame_base64": "data:image/jpeg;base64,...",
      "target_clarity": "good",
      "hand_occlusion": "low",
      "recognition_confidence": "high",
      "appearance_summary": "白色长方体纸盒，蓝色文字"
    }
  ]
}
```

同一个 `event_id + food_index` 重发时，数据库事务返回原处理结果，不会重复创建、合并或删除库存。图片失败不阻止名称明确的库存动作；失败事件会在 Pi 本地排队并在后续联网时重试。

## 6. 入库决策规则

## 6.1 普通新入库

收到 `direction = in` 且 `gesture = false` 后：

1. 清理模型返回并验证字段。
2. 标准化食材名称。
3. 查询 `shelf_life_rules` 保质期参考表。
4. 如果参考表已有该食材，直接使用记录的默认天数。
5. 如果参考表没有该食材，让 LLM 按普通超市购买、家用冰箱冷藏和保守估算原则返回常见保质期，并将结果写入参考表。
6. 计算新食材的预计到期日。
7. 查询库存中相同 `canonical_name` 的未删除条目。
8. 按以下规则创建或合并。

## 6.2 同名绿色食材合并

如果冰箱内已有同名食材，并且已有条目状态为绿色：

- 不创建新的可见库存条目。
- `expiry_date` 取旧条目与新入库预计到期日中更早的日期。
- `shelf_life_days` 根据最终最早到期日同步更新或保留为参考值。
- `last_added_at` 更新为当前时间。
- 最佳帧加入该条目的后台参考图片集合。
- 参考图片最多保留 3 张。

这相当于采用保守原则：合并后整组食材按较短的剩余保质期展示。

示例：

- 现有土豆剩余 10 天，为绿色。
- 新放入土豆预计剩余 14 天。
- 合并后仍然只有一个“土豆”条目，到期时间按剩余 10 天计算。

## 6.3 同名条目为橙色或红色

如果已有同名条目已经临期或过期，不与新入库食材合并：

- 创建一个新库存条目。
- 新条目使用新的入库日期和保质期。
- 原有临期条目继续排在上方。

这样可以避免新鲜食材被旧批次的临期状态长期绑在一起。

## 6.4 同时存在多个绿色同名条目

如果历史数据中已经存在多个绿色同名条目：

- 先合并为一个绿色条目。
- 到期日取最早日期。
- 参考图片合并后保留质量最好的 3 张。

## 6.5 放回手势

收到 `gesture = true` 的入库事件时：

- 如果当前库存存在同名条目，直接匹配该条目并视为放回，不创建或修改库存。
- 不刷新入库日期、保质期或到期日。
- 可以用本次更清晰的画面更新后台参考图片。
- 如果当前库存没有同名条目，查询当天同名的出库记录。
- 找到当天同名出库记录时，恢复被该记录软删除的原库存条目，包括原入库日期、保质期、到期日和参考图片。
- 当天存在多条同名出库记录时，优先恢复最近一条尚未恢复的记录。
- 如果当天也没有同名出库记录，则退化为普通新入库，并在事件日志中注明 `return_not_found`。

## 7. 出库决策规则

V1 使用“名称优先、全部图片兜底、无可靠目标则不动作”的策略。

> 设计解释：原讨论中的“没有很相似的就直接出库”无法确定要删除哪一条库存，因此 V1 按此前原则实现为“没有很相似的就不执行出库”。如果这里原意不同，需要在开发前修改本节。

## 7.1 第一步：识别出库食材

模型分析出库连拍，返回：

- 食材名称。
- 标准名称。
- 最佳帧序号。
- 目标清晰度和手部遮挡程度。
- LLM 综合上述证据给出的最终识别置信度。
- 简短外观描述。

## 7.2 第二步：按名称查库存

如果库存中存在相同 `canonical_name`：

- `recognition_confidence = high` 时，直接执行出库并软删除匹配条目。
- 若同名食材存在多个批次，优先删除到期时间最早的条目。
- `recognition_confidence = medium` 或 `low` 时，只对本次出库最佳帧和同名库存的主要参考图做“明显不符检查”。
- 如果只有一个同名条目且图片没有明显不符，即使画面不够清楚，也允许名称匹配通过并执行出库。
- 如果存在多个同名批次，逐个排除明显不符的候选，然后在剩余候选中删除到期时间最早的一条。
- 只有所有同名候选都确认明显不符时，才阻止按名称出库，并进入全库存图片兜底匹配。

V1 不要求模型辨认同一组散装土豆中的具体哪一个土豆。

明显不符检查使用独立 prompt：

```text
图片 A 是本次拿出冰箱的食材，图片 B 是库存中同名食材的参考图。

这里只检查两者是否存在“明显不符”，不要要求它们必须高度相似：
- 拍摄角度不同、光照不同、轻微模糊、局部遮挡，不算明显不符；
- 只有食材种类、包装形状、主要颜色、容器形式或明显标志清楚地互相矛盾时，才算明显不符；
- 证据不足或无法确定时，一律返回 false。

只返回 JSON：
{
  "obvious_mismatch": false,
  "reason": "没有发现足以否定名称匹配的明显矛盾"
}
```

## 7.3 第三步：全库存图片兜底匹配

出现以下情况时启用：

- 名称在库存中没有匹配。
- 名称虽然匹配，但明显不符检查返回 `true`。
- 模型名称可能使用了完全不同的叫法。

发送给 Qwen-VL：

- 本次出库最佳帧。
- 当前所有有效库存条目的主要参考图片。
- 每张候选图片对应的不可猜测 ID。
- 要求只根据外观相似性判断，不依据候选名称强行匹配。

模型返回：

```json
{
  "matched_inventory_id": "uuid-or-null",
  "visual_similarity": "high",
  "reason": "包装颜色、盒体形状、蓝色标志和瓶盖位置高度一致"
}
```

只有 `visual_similarity = high` 时才执行出库。medium、low 或 null 均不修改库存。

V1 为控制延迟和图像 token：

- 每个库存条目只上传 1 张主要参考图。
- 图片使用压缩后的匹配版本，不上传原始高分辨率照片。
- 如果库存规模超过模型一次请求的稳定处理能力，应分批比较，再对每批第一名做最终复核。
- 第一版可以先以 24 张为单批上限，实际值通过真机测试调整。

## 7.4 无可靠匹配

如果没有高度相似的库存图片：

- 不删除任何库存条目。
- App 普通首页不显示本次失败事件。
- 后台保存事件和最佳帧，动作记录为 `no_action`。
- 后续可以增加“待确认”调试页，但不属于 V1 主界面。

## 7.5 并发与重复事件

每次识别事件必须具有唯一 `event_id`。数据库更新在事务中完成：

- 同一事件重复上传不得重复创建或删除库存。
- 软删除后的条目不能再次被自动删除。
- 同一条已删除记录不能被两个放回事件重复恢复。

## 8. 后续外观特征方案

V1 暂不按食材类别筛选图片，因为食材名称识别不准确时，类别判断也可能同时出错。

后续版本在入库时生成结构化外观档案：

```json
{
  "dominant_colors": ["white", "blue"],
  "shape": "rectangular_carton",
  "packaging": "paper_carton",
  "container": "sealed_box",
  "surface": "smooth",
  "visible_text": ["MILK"],
  "distinctive_marks": ["blue band", "white screw cap"],
  "size": "medium"
}
```

外观特征用于缩小候选范围，而不是直接决定删除：

1. 根据颜色、形状、包装形式和可见文字计算粗相似度。
2. 取最相似的少量候选。
3. 再让视觉模型比较真实图片。
4. 最终仍遵守低置信度不修改库存的原则。

更后期可加入图像向量模型，把所有库存图片转成向量。出库时先进行本地或云端近邻检索，再把前几名交给 Qwen-VL 复核。

## 9. 菜谱功能

## 9.1 入口

冰箱页面底部固定一个柔和但明显的 `生成菜谱` 按钮。普通浏览食材不会自动调用模型，也不在每个条目下直接展开菜谱。

## 9.2 食材选择模式

点击 `生成菜谱` 后：

1. 所有食材条目整体向右平移动画。
2. 条目左侧出现圆形勾选框。
3. 橙色临期食材自动勾选。
4. 绿色食材默认不选，但可手动勾选。
5. 红色过期食材默认不选，并显示过期提示。
6. 用户可以取消任何自动勾选的橙色食材。
7. 底部按钮变为 `用所选食材生成菜谱`。

至少选择一个食材后才能生成。

## 9.3 菜谱选项

生成时直接使用设置页保存的菜系。可选菜系包括：不限、中餐、日式、韩式、意大利、墨西哥、东南亚、印度、地中海、美式家常和西式简餐。V1 不增加人数、时间、辣度或饮食限制设置。

## 9.4 菜谱提示词原则

模型必须：

- 优先使用勾选食材。
- 不强制使用全部勾选食材。
- 每份生成结果必须至少实际使用一种已勾选食材；如果一种都无法合理使用，应返回无法生成，而不是提供无关菜谱。
- 尽量减少需要额外购买的主要食材。
- 可以默认盐、油、糖、酱油等基础调味料存在。
- 明确列出仍然缺少的非基础材料。
- 输出菜名、用时、份量、材料和分步做法。
- 不建议使用已明确过期的食材。

## 9.5 结果页

菜谱结果页显示：

- 菜名。
- 使用了哪些库存食材。
- 还缺哪些材料。
- 预计时间和份量。
- 分步骤做法。
- `重新生成` 和 `返回冰箱`。

V1 不在菜谱生成后自动扣减库存。用户做完菜后仍由摄像头出库事件或手动删除更新库存。

相同食材组合和相同设置产生的结果可以缓存，以减少重复调用。

## 10. 厨师思考动画

菜谱生成期间，在页面中央显示半透明浮层：

- 一个卡通小厨师托着下巴思考。
- 头顶气泡循环出现。
- 可以有轻微眨眼、点头或帽子上下浮动。
- 背后的冰箱内容轻微模糊，但仍可辨认。
- 文案在以下内容间轮换：
  - `看看冰箱里有什么…`
  - `正在搭配食材…`
  - `马上开饭…`

动画应支持减少动态效果设置。请求超过合理时间后显示重试按钮，不能无限加载。

实现上不需要依赖其他 AI。可以先生成一套统一手帐风格的小厨师角色素材，再使用 SwiftUI 对眼睛、帽子、身体和思考气泡做轻量动画；也可以输出少量透明背景帧制作循环动画。V1 优先采用 SwiftUI 分层动画，体积小、容易适配深浅色和“减少动态效果”。

## 11. 设置页

设置页只保留三个选项：

### 树莓派

- 检测开门。
- 连拍并调用 Qwen-VL。
- 清理模型 JSON。

- 在需要时调用全库存视觉比较。

- PostgreSQL：库存、设置和事件。

- Edge Function 或独立后端：处理需要密钥的模型调用和数据库事务。

Supabase Secret key、service role、数据库密码及模型 API Key 均不得放进 iOS App。树莓派后续通过带独立设备凭证的 Edge Function 上传事件，不直接持有 Supabase Secret key。

### iOS App

- 展示实时库存。
- 编辑、软删除和撤销。
- 进入菜谱选择模式。
- 展示生成结果与同步状态。

## 14. 容错原则

1. 模型返回内容必须经过 JSON 清理和字段验证。
2. `foods` 与方向数组不一致时不直接更新库存。
3. 识别失败不影响持续监听下一次开门。
4. 数据库操作必须幂等。
5. 出库无可靠目标时不删除。
6. App 手动修正优先级高于模型结果。
7. 删除使用软删除并保留撤销窗口。
8. 图片上传失败不阻止名称明确的新食材入库，但应记录图片缺失。
9. 菜谱服务失败不影响库存功能。

## 15. V1 验收标准

### UI

- 首页呈现明确的打开卡通冰箱造型。
- 库存可连续纵向滚动。
- 食材严格按到期时间排序。
- 红、橙、绿颜色柔和且配有文字状态。
- 整体呈现卡通、生活化、手帐风格。
- 顶部不显示库存总数，只用小字显示最后同步时间。
- 名称和保质期可修改。
- 编辑界面只显示一个食材名称，不暴露后台标准名称。
- 首页可以通过 `＋` 按钮手动添加食材。
- 手动添加时可以设置名称、入库日期和保质期，并遵守同名绿色合并规则。
- 左滑可以删除，5 秒内可以撤销。
- 参考图片不会显示在普通 App 页面。

### 入库

- 每个食材能够保存最佳帧序号和私有参考图。
- LLM 会先判断目标清晰度和手部遮挡程度，再直接给出最终识别置信度，后端不计算加权分数。
- 新食材第一次入库时能够生成并保存默认保质期，以后优先复用参考表。
- 同名绿色食材不会创建新的可见条目。
- 合并后仍然只保留“是否存在”的单个可见条目。
- 合并后的到期日取较早日期。
- 同名橙色或红色食材与新鲜批次分开保存。
- 放回手势不刷新保质期。
- 无同名库存的放回事件能够恢复当天最近一条同名出库记录。

### 出库

- 高置信度同名食材能够直接软删除。
- 中低置信度同名食材只做明显不符检查；没有明显不符时仍能正常出库。
- 同名图片确认明显不符时不会误删该条目，并会进入全库存图片比较。
- 没有名称匹配时可以调用全库存图片比较。
- 只有高度相似时才删除候选库存。
- 无高度相似候选时库存不变化。
- 重复事件不会重复删除。

### 菜谱

- 点击按钮后条目右移并出现勾选框。
- 橙色食材自动勾选且可以取消。
- 红色过期食材不会自动勾选。
- 用户可以额外勾选绿色食材。
- 可以在设置中选择菜系。
- 生成期间显示厨师思考动画。
- 结果优先使用选择的临期食材，不强制全部使用，但至少使用一种已选食材。

## 17. V1 已确定的关键产品决策

1. 最佳帧只保存在后台，不在普通 UI 中显示。
2. 库存按到期时间从近到远排列。
3. 同名绿色食材合并，保质期按更短的一批计算。
4. 同名临期或过期食材不与新鲜批次合并。
5. V1 不依赖食材类别缩小候选。
6. 名称匹配失败时允许比较全部库存的主要参考图片。
7. 只有高度相似的图片候选才能触发删除。
8. 无可靠匹配时不修改库存，失败事件只保留在后台。
9. 菜谱按需生成，橙色食材自动勾选，红色食材不自动使用。
10. 库存只记录是否存在，不记录数量；容器内部数量逻辑留到后续版本。
11. 首次出现的食材由 LLM 给出保守的常见冷藏保质期，并缓存到参考表。
12. 放回事件优先匹配现有同名库存，否则恢复当天最近的同名出库记录。
13. 设置页只保留临期阈值、菜系和提醒开关。
14. 置信度由 LLM 综合清晰度、遮挡和识别把握直接给出，后端不做数值加权。
15. 同名但中低置信度时只检查是否明显不符；无法确定不算不符，默认允许出库。
16. App 只展示一个可编辑食材名称，后台标准名称自动生成并对用户隐藏。
17. 用户可以手动添加食材，手动添加仍遵守现有合并和保质期规则。
18. 后续优化方向是结构化外观特征和视觉向量检索。
